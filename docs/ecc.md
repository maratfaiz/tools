# ECC (Engineering Control Center) — «операционная система» для Claude Code

## Что это на самом деле (без жаргона)

Сам по себе Claude Code — это просто «умный исполнитель»: ты пишешь ему задачу, он пишет код. Без ECC он не помнит, что вчера вы договорились всегда писать тесты сначала, не проверяет сам себя после того как что-то написал, и в новом чате про твой личный стиль код-ревью снова придётся напоминать заново — с чистого листа каждый раз.

**ECC — это не программа и не сервис. Это набор файлов-инструкций**, которые лежат в репозитории и Claude Code читает их автоматически при старте. По сути — это как нанять не одного фрилансера, который делает что в голову взбредёт, а небольшую инженерную команду с прописанным процессом: есть тот, кто сначала планирует, есть тот, кто потом проверяет свежим взглядом, есть свод правил по стилю кода на каждом языке, и всё это включается само, без напоминаний.

### Конкретный пример: как выглядит разница

**Без ECC**, если попросить «добавь логин через OAuth»:
- Claude сразу пишет код
- Тесты может не написать, если явно не попросить
- Ревью своего же кода делает тем же контекстом, который его писал — то есть теми же «слепыми пятнами»
- Стиль кода — какой получится, если явно не задать правила

**С ECC** та же задача выглядит так:
```
/plan "добавь логин через OAuth"
```
1. Отдельный **агент** `planner` (см. ниже, что это) сначала пишет план: что делать, в каком порядке, какие риски
2. При реализации активируется **skill** `tdd-workflow` — он буквально не даёт писать код раньше теста: сначала пишем тест, который падает (RED), потом код, который его чинит (GREEN), потом чистим (REFACTOR)
3. Команда `/code-review` — Claude запускает **другого** агента `code-reviewer` **в новом, чистом контексте**, у которого нет истории «как я это писал» — он смотрит на код глазами постороннего и находит то, что автор кода не заметил бы сам
4. Всё это время в фоне подгружены **rules** — например `rules/typescript` — которые говорят «не хардкодь секреты, используй эти паттерны обработки ошибок» — не нужно писать это в промпте каждый раз, оно уже «в воздухе»

Ничего из этого не магия — просто заранее написанные Markdown-инструкции, которые Claude Code подхватывает сам.

### Четыре строительных блока ECC

| Блок | Что это простыми словами | Пример |
|---|---|---|
| **Агенты** (68 шт.) | Мини-Claude с узкой ролью и своим (часто «чистым») контекстом — вызывается под конкретную задачу | `planner` планирует, `security-reviewer` ищет уязвимости, `build-error-resolver` чинит упавшую сборку |
| **Skills** (286 шт.) | Инструкция-плейбук «как делать X» — та же механика, что у Higgsfield/Graphify/UI UX Pro Max skills, просто для общей инженерии | `tdd-workflow` — как писать тесты сначала; `django-patterns` — как правильно строить Django-приложение |
| **Команды** (94 шт.) | Слэш-команда — короткий ярлык вместо длинного промпта, сразу запускает нужный agent/skill | `/code-review`, `/build-fix`, `/security-scan` |
| **Rules** | Всегда-загруженные стандарты по языку/фреймворку — не нужно повторять в каждом сообщении | `rules/typescript/security.md`, `rules/python/testing.md` |
| **Хуки** | Автоматика на события (до/после вызова инструмента) — например блокировка `rm -rf` или автоформат после правки | GateGuard блокирует опасные shell-команды до выполнения |

Rules и hooks — это «фон», который просто есть и работает. Agents/skills/commands — то, с чем реально взаимодействуешь через `/команды` или обычным текстом.

### Зачем это вообще нужно

- **Не объяснять одно и то же заново.** Стандарты (TDD, 80% покрытия тестами, не хардкодить секреты) прописаны один раз в rules и работают в каждой сессии.
- **Ревью «чужими глазами».** Агент, который проверяет код, не тот же контекст, что его писал — меньше шанс пропустить свою же ошибку.
- **Специалисты под задачу.** Вместо одного универсального Claude — узкие агенты под конкретный тип работы (безопасность, конкретный язык, починка сборки), которые лучше справляются именно с этим.
- **Экономия времени на рутине.** `/build-fix`, `/refactor-clean`, `/security-scan` — вместо того, чтобы формулировать это промптом каждый раз.

## Установлено прямо в этот репозиторий

ECC уже стоит здесь, project-local, под `.claude/` (профиль `developer`, таргет `claude-project` — официальный установщик ECC, не плагин-путь). Это значит: как только Claude Code открывает этот репозиторий, все агенты/skills/команды/rules из ECC подхватываются автоматически, ничего доустанавливать не нужно.

Что реально приехало (807 файлов): агенты (`.claude/agents/`), skills (`.claude/skills/`), команды (`.claude/commands/`), rules по всем языкам/фреймворкам (`.claude/rules/ecc/*` — common, typescript, python, golang, react, vue и т.д.), конфиг хуков (`.claude/hooks/`) и MCP-шаблоны (`.claude/mcp-configs/`).

**Важный нюанс про хуки:** файл `.claude/hooks/hooks.json` физически лежит в репозитории, но сам по себе Claude Code его не подхватывает — project-local `claude-project`-установка не регистрирует хуки как активный runtime (это отличие от установки через `/plugin`, где Claude Code 2.1+ грузит `hooks.json` автоматически по конвенции). То есть агенты/skills/команды/rules работают сразу, а автоматические проверки (блокировка опасных команд, автоформат после правок и т.д.) — нет. Если понадобятся именно они, это отдельный шаг с официальным установщиком на своей машине (`./install.sh --target claude --modules hooks-runtime`) — см. `.claude/hooks/README.md`.

## Установка на своей машине (если Claude Code у тебя работает не только здесь)

Этот репозиторий — временная облачная сессия, она удаляется. Чтобы ECC был у тебя постоянно (на ноутбуке), там нужно поставить его отдельно — либо рекомендуемым plugin-путём (2 команды прямо в Claude Code):

```
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc
```

либо так же, как здесь — вручную скачать репозиторий и прогнать установщик:

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
npm install
node scripts/install-apply.js --target claude --profile developer   # глобально в ~/.claude
# или --target claude-project, если хочешь project-local как здесь
```

Проверить версию Claude Code перед установкой (нужно 2.1.0+): `claude --version`.

## Как этим пользоваться каждый день

| Что делаю | Команда |
|---|---|
| Начать новую фичу | `/plan "описание фичи"`, затем skill `tdd-workflow` |
| Чиню баг | сначала пишу тест, который его воспроизводит, дальше `tdd-workflow` |
| Прошу проверить код | `/code-review` (ревью со «свежим» контекстом) |
| Чиню упавшую сборку | `/build-fix` |
| Чищу мёртвый код | `/refactor-clean` |
| Проверяю, не забит ли контекст | `/context-budget` |
| Заканчиваю долгую сессию | `/save-session` или `/learn-eval` |
| Продолжаю позже | `/resume-session` |
| Проверяю безопасность своих агент-конфигов | `/security-scan` или `npx -y ecc-agentshield scan --path .` |

Типичная цепочка на фичу:
```
/plan "Add user authentication with OAuth"   -> planner делает план реализации
tdd-workflow (skill)                              -> tdd-guide заставляет писать тесты сначала
/code-review                                      -> code-reviewer проверяет результат
```

Ничего из этого не обязательно вызывать вручную каждый раз — можно просто описать задачу обычным текстом, и Claude сам решит, какой agent/skill уместен. Слэш-команды — это просто явный короткий путь, когда точно знаешь, что нужно.

## Важно по безопасности

Ставить ТОЛЬКО из официальных источников — сам GitHub-репозиторий `affaan-m/ECC`, npm-пакеты `ecc-universal`/`ecc-agentshield`, или их официальный GitHub App. Авторы прямо предупреждают: сторонние зеркала/копии могут содержать вредоносный код.

## Если что-то пошло не так

```bash
node scripts/ecc.js doctor      # диагностика
node scripts/ecc.js repair      # почини
node scripts/uninstall.js --dry-run   # что удалится
node scripts/uninstall.js       # удалить
```

## Справочник команд

Всего установлено 94 слэш-команды в `.claude/commands/`. Ниже — подробно по самым востребованным, сгруппированным по задачам; однотипные семейства (per-language build/review/test, epic-*, multi-*, prp-*) описаны один раз с полным списком вариантов, чтобы не повторять одну и ту же структуру 94 раза. Полный список имён файлов — `ls .claude/commands/`.

**Важно про синтаксис:** это project-local установка (не через `/plugin`), поэтому команды вызываются **без префикса** — `/plan`, не `/ecc:plan`.

### Планирование и разработка фичи

#### `/plan [описание фичи | путь/к/файлу.prd.md]`
- **Что делает:** переформулирует требования, оценивает риски, создаёт пошаговый план реализации. **Ждёт твоего подтверждения**, прежде чем трогать код.
- **Пример:** `/plan "добавить логин через OAuth с Google"`

#### `/plan-prd [идея продукта/фичи]`
- **Что делает:** сначала генерирует лёгкий, «problem-first» PRD (документ с требованиями), потом передаёт его в `/plan`. Без аргумента — начнёт с вопросов.
- **Пример:** `/plan-prd "личный трекер привычек"`

#### `/feature-dev`
- **Что делает:** управляемая разработка фичи с акцентом на понимание существующей архитектуры проекта перед написанием кода.

#### `/project-init`
- **Что делает:** определяет стек проекта и строит dry-run план онбординга ECC под него (что из профилей/модулей подходит именно этому проекту).

### Ревью и починка кода

#### `/code-review [pr-номер | pr-url | пусто]`
- **Что делает:** ревью изменений — без аргумента смотрит локальные незакоммиченные правки, с номером/ссылкой — конкретный GitHub PR.
- **Пример:** `/code-review 42`

#### `/review-pr [pr-номер | pr-url | пусто]`
- **Что делает:** более развёрнутое ревью PR с несколькими специализированными агентами одновременно (а не одним code-reviewer).

#### `/build-fix`
- **Что делает:** определяет систему сборки проекта и чинит ошибки сборки/типов небольшими, безопасными правками по одной.

#### `/refactor-clean`
- **Что делает:** находит и безопасно удаляет мёртвый код, с проверкой (тесты/сборка) после каждого удаления.

#### `/quality-gate`
- **Что делает:** прогоняет ECC-форматтер и чек качества для одного файла, печатает что нужно исправить.

#### `/test-coverage`
- **Что делает:** анализирует покрытие тестами, находит пробелы, генерирует недостающие тесты до целевого порога (80%).

#### `/harness-audit`
- **Что делает:** детерминированный аудит самого репозитория (не кода продукта, а конфигурации агента/харнесса) с приоритизированной оценкой.

### Безопасность

#### `/security-scan`
- **Что делает:** прогоняет AgentShield по агентам, хукам, MCP-конфигам, правам и секретам — ищет уязвимости именно в настройке самого Claude Code, не в коде проекта.
- **Эквивалент напрямую:** `npx -y ecc-agentshield scan --path .`

### Работа с сессией и памятью

#### `/save-session`
- **Что делает:** сохраняет состояние текущей сессии в датированный файл в `~/.claude/session-data/`, чтобы продолжить с полным контекстом позже.

#### `/resume-session`
- **Что делает:** загружает самый свежий файл сессии и продолжает работу с того места, где остановились.

#### `/sessions`
- **Что делает:** управление историей сессий — список, алиасы, метаданные.

#### `/learn`
- **Что делает:** вытаскивает из текущей сессии повторяемые паттерны и сохраняет как кандидатов в skills/правила.

#### `/learn-eval`
- **Что делает:** то же самое, что `/learn`, но сначала сам оценивает качество находки и решает — сохранить в проектный или глобальный scope.

#### `/checkpoint`
- **Что делает:** создаёт/проверяет/печатает список контрольных точек воркфлоу после прогона проверок — чтобы можно было откатиться к последнему проверенному состоянию.

#### `/cost-report [csv]`
- **Что делает:** локальный отчёт по затратам (токены/стоимость) из ECC cost-tracker. `csv` — вывод в csv вместо текста.

#### `/prune`
- **Что делает:** удаляет накопленные «instincts» (кандидаты в паттерны) старше 30 дней, которые никогда не были продвинуты в реальный skill/rule.

#### `/instinct-status` / `/instinct-export` / `/instinct-import`
- **Что делает:** `status` — показать накопленные instincts (проектные + глобальные) с уровнем доверия; `export` — выгрузить в файл; `import` — загрузить из файла/URL.

#### `/promote`
- **Что делает:** поднимает instinct из проектного scope в глобальный (работает во всех проектах, не только в этом).

#### `/evolve`
- **Что делает:** анализирует накопленные instincts и предлагает/генерирует из них более развитую структуру (skill, rule и т.п.).

### Хуки на заказ (hookify)

#### `/hookify [описание нежелательного поведения]`
- **Что делает:** создаёт хук, который предотвращает конкретное нежелательное поведение, по анализу переписки или явному описанию.
- **Пример:** `/hookify "не давай коммитить без запуска тестов"`

#### `/hookify-list` / `/hookify-configure` / `/hookify-help`
- **Что делает:** `list` — показать все настроенные правила hookify; `configure` — включить/выключить интерактивно; `help` — справка по системе.

### GitHub / PR

#### `/pr [base-ветка]`
- **Что делает:** создаёт GitHub PR из текущей ветки с непушнутыми коммитами — сам находит шаблон PR, анализирует изменения, пушит. По умолчанию база — `main`.

### Мульти-модельные воркфлоу (несколько LLM в одной задаче)

| Команда | Что делает |
|---|---|
| `/multi-plan` | план реализации несколькими моделями одновременно, без изменения кода |
| `/multi-execute` | выполняет такой план — Claude остаётся единственным, кто пишет на диск |
| `/multi-backend` | мульти-модельный проход фокусированно на backend (API, алгоритмы, данные) |
| `/multi-frontend` | то же самое для frontend (компоненты, вёрстка, анимация) |
| `/multi-workflow` | полный цикл: research → plan → execute → optimize → review, несколькими моделями |

### Orchestration (сквозные автоматизированные процессы)

| Команда | Что делает |
|---|---|
| `/orch-add-feature` | новая фича с нуля end-to-end: research → plan → TDD → review → commit с гейтом |
| `/orch-build-mvp` | рабочий MVP из спеки/дизайн-документа: разбор → нарезка → скаффолд → TDD → review |
| `/orch-change-feature` | меняет поведение существующей рабочей фичи: тесты под новую спеку → реализация → review |
| `/orch-fix-defect` | баг: сначала воспроизводящий регрессионный тест → фикс до зелёного → review |
| `/orch-refine-code` | рефакторинг с сохранением поведения: тесты зелёные → до → после снова зелёные → review |
| `/orch-review` | прогоняет ревью по дифу (локальному или PR), разделяет находки на блокирующие и совещательные |

### Per-language build / review / test (одинаковый паттерн на каждый язык)

Для каждого языка — ровно три параллельные команды с одним и тем же смыслом:
- **`<lang>-build`** — находит и чинит ошибки сборки/линтера минимальными правками (вызывает `<lang>-build-resolver` агента)
- **`<lang>-review`** — ревью на идиоматичность, безопасность, специфичные для языка проблемы (вызывает `<lang>-reviewer` агента)
- **`<lang>-test`** — TDD-цикл: тесты сначала, покрытие 80%+

Доступные языки: **go, rust, kotlin, flutter, cpp**. Плюс ревью без своей build/test-команды: `python-review`, `vue-review`, `fastapi-review`, `react-build`/`react-review`/`react-test`, `gradle-build`.

**Пример:** `/go-test` → пишет табличный тест → `/go-build` → чинит если не собралось → `/go-review` → ревью перед коммитом.

### PRP-пайплайн (альтернативный, более интерактивный путь план→код→PR)

| Команда | Что делает |

### Разное

| Команда | Что делает |
|---|---|
| `/aside [вопрос]` | ответить на короткий побочный вопрос без потери контекста текущей задачи, потом вернуться к ней автоматически |
| `/model-route` | рекомендует модель (Haiku/Sonnet/Opus) под текущую задачу по сложности/риску/бюджету |
| `/update-docs` | синхронизирует документацию из source-of-truth файлов (схемы, роуты, экспорты) |
| `/update-codemaps` | сканирует структуру проекта и строит компактные архитектурные карты |
| `/skill-create` | анализирует git-историю проекта и генерирует `SKILL.md` из найденных паттернов |
| `/skill-health` | дашборд здоровья всех установленных skills |
| `/plan-canvas [путь]` | открывает план/HTML-артефакт в браузере для аннотирования и согласования визуально |
| `/projects` | список известных проектов и статистика их instincts |
| `/jira [запрос]` | получить тикет Jira, проанализировать требования, обновить статус или оставить комментарий |
| `/pm2` | анализирует проект и генерирует PM2-команды под найденные сервисы |
| `/setup-pm` | настроить предпочитаемый пакетный менеджер (npm/pnpm/yarn/bun) |
| `/gan-build` / `/gan-design` | цикл генератор↔оценщик с ограниченным числом итераций — для реализации или дизайна соответственно |
| `/santa-loop` | два независимых ревьюера-модели должны оба одобрить код, прежде чем он уйдёт дальше |
| `/loop-start` / `/loop-status` | запустить управляемый автономный цикл с защитными условиями останова / посмотреть его текущее состояние |
| `/marketing-campaign [бриф]` | полная маркетинговая кампания из брифа — позиционирование, лендинг, email-цепочка, соцсети, объявления, видео-скрипты |
| `/auto-update` | подтягивает последние изменения ECC-репозитория и переустанавливает текущие managed-таргеты |
